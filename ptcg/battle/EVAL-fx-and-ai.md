# 评估：战斗表现优化 与 对手 AI / 卡组理解优化

## 背景
评估对象：ptcg/battle 的「战斗表现」与「对手 AI + 卡组理解」两项优化。当前已有基础动画设施与三层 AI，但都缺关键挂钩。用户希望：⑤ 优化召唤/收回/击倒/技能/受击表现，技能需分近战/远程/辅助；⑥ 优化对手 AI 表现与卡组理解，并可在卡组里写玩法注释供 AI 读取。

【现状取证结论】
⑤ 战斗表现：
- CSS 已有 6 个 keyframes：lunge-pl / lunge-opp（突进）、hitFlash（受击闪）、enterScale（登场）、exitScale（退场）、fadeIn
- JS 已有：_playAttackAnimAsync / _playAttackAnim / _animateHit / _animateEnter / _animateExit，时序硬编码（受击 560ms、换人 650ms）
- 缺口：① 无近战/远程/辅助区分；② 无伤害数字；③ 无击倒/拿奖赏卡表现；④ 无异常状态动画；⑤ 无音效
- **关键成本点**：招式效果在 BattleEngine.attack() 内部一次性执行到底，只暴露 cb.onLog / onPhaseChange / onFieldUpdate / onAiAction / onAiThinking，**没有「招式结算/命中」事件** → 想让弹道命中与结算对齐，必须新增事件或拆分 attack() 为两段
- 仓库体积敏感（ptcg/images 552MB）→ 音效若用音频文件会明显增加体积，建议 WebAudio 程序化音效（几 KB）

⑥ 对手 AI：
- 已有三层：AiPolicy.js（347 行，HeuristicPolicy 打分 + LlmPolicy 关键决策问 LLM）、DeckPlan.js（211 行，按卡组特征归类 archetype → weights）、AiSettings.js（105 行，与 ptcg 共享 DeepSeek key/model）
- 卡组存储：ptcg localStorage 'ptcg_decks'，结构 { name, cards: [...] }，DeckSource._normalize 读取 → 增加 notes/strategy 字段成本极低
- **关键成本点1**：没有任何自对弈/自动对战基准，无法度量 AI 改动是否变强（现状 grep 无 autobattle/selfPlay）
- 已有 aiPickHandler / aiPokemonPickHandler / aiActionHandler 路由，可支持无人值守对局

【用户要求】给出评估（成本 + 方案），未获批前不动手大改。

## 当前结论
- ⑤ 现状：动画骨架已有（6 keyframes + 4 个 animate 方法），但只区分「突进/受击/登场/退场」，没有招式类型概念，也没有伤害数字与击倒表现。
- ⑤ 真正的成本不在动画本身，而在事件时机：attack() 内部一次性执行完伤害+效果+换人，UI 只能在 attack() 返回后补动画，因此「弹道命中→伤害数字→受击」无法精确对齐。需要新增 cb.onAttackResolve（招式结算前/后各一次）或把 attack() 拆成前摇/结算两段。
- ⑤ 近战/远程/辅助的判定可以纯启发式得出，不必逐卡标注：伤害>0 且招式文本无「放置/指示物/对方场上」等远程特征→近战；伤害=0 或文本含「从弃牌区/牌库/放置伤害指示物/回复」→辅助；含「光束/波/弹/箭/喷射/落雷」等关键词→远程。可先用关键词表覆盖，命中率不足再补卡表。
- ⑤ 音效不要用音频文件：仓库已 552MB 图片，音频会继续膨胀且手机 PWA 首屏更慢；用 WebAudio 程序化合成（正弦/噪声包络）即可得到打击音、回复音、击倒音，体积几乎为 0。
- ⑥ 现状 AI 已有三层结构（启发式打分 + LLM 关键决策 + 卡组画像权重），「卡组里写玩法注释」落地成本很低：tpct 卡组对象加 notes/strategy 字段即可，DeckSource 读取后注入 AI。
- ⑥ 最大的隐藏成本是「无法度量」：目前没有自对弈基准，任何 AI 改动都无法判断是变强还是变弱。建议先做基准（无人值守 AI vs AI 跑 N 局统计胜率/回合数/断线率），否则后续优化全是凭感觉。
- ⑥ 「卡组注释」有两种用法，价值差异很大：① 仅注入 LLM prompt（成本低、效果依赖模型，但立竿见影）；② 解析成结构化指令（主力宝可梦/进化链/能量配比/关键道具/优劣对局）驱动启发式打分权重（成本高、但可离线、稳定、可测）。建议先①后②。

## 方案对比
- ⑤ 表现：A 只做 P0 表现补齐（约 1 天，纯 UI，零引擎风险）；B 做 P0+P1 招式类型化（约 2-3 天，需新增攻击结算事件，有引擎回归风险）；C 全做含音效与逐卡特效（约 4-6 天，需引入资源与体积权衡）。
- ⑤ 招式类型判定：A 纯关键词启发式（0.5 天，可能对少数卡不准，可后续加卡表覆盖）；B 启发式 + 人工标注表（先标高频招式，成本 +1 天）。
- ⑥ 卡组注释：A 仅注入 LLM prompt（约 0.5-1 天）；B 结构化指令解析驱动启发式权重（约 2-3 天）；C 再加自对弈度量基准（约 0.5-1 天，强烈建议与 A/B 同时做）。
- ⑥ AI 增强：A 战术目标（L3 局面目标 + 训练家前置有效目标判定）；B 能量长期规划与硬币期望值；C 决策可观测性（记录每步打分与理由，便于复盘与调参）；D 自对弈训练/搜索（长期项，不纳入本轮）。

## 推荐方案
建议顺序：⑤ 先做「招式结算事件 + P0 表现补齐」（低风险、用户立刻可见），招式类型化随后；⑥ 先做「自对弈度量基准」（否则后续 AI 改动不可验证），紧接着做「卡组玩法注释注入 LLM prompt」——这是用户点名的需求且成本最低、收益最直接。两项的关键前提都是先补「可观测性」：⑤ 缺招式结算事件，⑥ 缺对局统计基准。

## 风险与边界
- ⑤ 拆分或挂钩 attack() 属于引擎改动，历史经验表明引擎改动容易触发连锁回归（本会话多次踩坑：宽正则会连锁破坏解析、TDZ 静默失败）。建议以「新增事件回调」而非「重写 attack()」的方式实现，保持原有同步执行顺序不变。
- ⑤ 动画时序硬编码（560/650ms）会让长动画拖慢操作节奏；手机低端机可能卡顿。建议统一走一个动画时长常量并支持「关闭动画/加速」。
- ⑥ 卡组注释是玩家自由文本，若直接拼进 LLM prompt 存在注入风险（例如注释里写「忽略规则」），且会占用上下文。建议限长、转义、并明确标注为「玩家策略建议」而非规则。
- ⑥ 若注释内容与实际卡组不符（例如写的卡不在卡组里），AI 会被误导。建议做一致性校验：注释中提到的卡名若不在卡组中则丢弃并提示。
- ⑥ 没有基准就优化 AI，无法区分「变强」和「换了运气」，也无法防止回归。

## 验证方式
- ⑤ 建议分三批：P0 表现补齐（伤害数字 + 击倒/拿奖赏卡表现 + 登场/收回动画 + 状态动画，纯 UI 层，不碰引擎）；P1 招式类型化（moveType 启发式 + 近战/远程/辅助三套动画 + 新增 onAttackResolve 让弹道与结算对齐）；P2 打磨（逐卡特效、屏幕震动、程序化音效）。
- ⑥ 建议分三批：P0 度量基准（无人值守 AI vs AI 自对弈跑批 + 胜率/回合数/异常统计）；P1 卡组注释（笔记字段 + 卡组编辑 UI + 注入 LLM prompt）；P2 结构化指令解析驱动打分权重 + 关键局面（进化链、能量规划、有效目标前置判定）。
- 两项都建议先做「可观测」再做「更强」：⑤先加招式结算事件，⑥先加自对弈基准。
